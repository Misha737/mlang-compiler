statement ::= decl | assign | if | while | print | lambda
lambda ::= "fn" ident ":=" "[" [ ident { "," ident } ] "]" "(" [ type ident { "," type ident } ] ")" "->" type NL block
A lambda is a statement: it may stand at the top level among the statements and inside any block (function, member function, if, while, another lambda). A line starting with fn name := [ is a lambda. fn name := without [ inside a block stays an error, and a capture list on a member function (inside a struct) stays an error. Add a LambdaNode (name, captures with line:col for each, params, result type, body) and make --ast print it as the parse tree. The parser does not decide anything about names.

[mut n] in a capture list gives the lambda its own mutable copy of n.
- Parser: a capture may be written mut name. Add a mutable flag to CaptureNode; --ast prints it (for example Capture mut n, plain Capture k otherwise). The grammar file grammar.ebnf gets capture ::= [ "mut" ] ident. mut alone or mut without a name is a parse error with line:col.
- Semantic (visit_lambda): the generated struct field for a mut capture is mut (FieldNode.mutable = True, capture = True), so --ast-checked prints Member n i32 mut. A capture without mut stays const, and assigning to it keeps the existing message (the capture is const, write [mut k]). A mut capture of a const variable is allowed, it is just a copy. The original variable is never changed: the lambda works only on its own field.
- A capture of another lambda is const unless written [mut next]. With [mut next] the field of type lambda.next is mut, so the call next() inside the body is allowed to change that copy.
- Mutation rule: a lambda call that assigns a mut capture (note_field_write sets assigns_field) is a mutating member function; also, call is mutating if it calls a mutating member through a mut capture (this_calls propagation in finish_member_calls). The existing rule for callable objects decides where it may be called, so no new rule is needed, only make sure the lambda's call method goes through the same register_member_function / call_sites / finish_member_calls machinery.
- The closure variable (the generated Decl <name> lambda.<name>) is mut exactly when at least one of its captures is mut (including a mut capture of a lambda), so next() at the place of the declaration works. A lambda with only const captures stays const (a call that cannot mutate is fine either way).
- Codegen should not need changes (the capture copy is still alloca + gep + store; the call function writes through this). Verify by running.
